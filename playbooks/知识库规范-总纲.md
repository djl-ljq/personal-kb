# 研发知识库 · 规范总纲 v1.0

> 适用对象：任何一个研发项目团队
> 交付形态：一棵目录树 + 两张记录表 + 三份规范文档。不需要装任何软件，不需要跑任何脚本。
> 核心机制：**人只提供内容和拍板，AI 负责按规范落位，全程通过 MCP 写入知识库。**

---

## 一、这套东西解决什么

研发过程中四类资产散落在各系统，导致四个断点：

| 断点 | 表现 |
| --- | --- |
| 找不到 | 文档在腾讯文档、飞书、邮件、群聊、个人电脑，没有统一入口 |
| 对不上 | 需求 ID ↔ 代码提交 ↔ 测试用例 ↔ Bug ↔ 发布单，彼此无关联，追溯靠人脑 |
| 带不走 | 没有离线副本，换人换电脑就断档 |
| 不敢共享 | 敏感配置和普通文档混放，没法按权限给新人或外部看 |

本规范不解"存哪"（存储由 MCP 平台负责），只解决"**放哪、叫什么、怎么记、谁在什么时候动**"。

## 二、一个项目空间长什么样

```
<项目空间>/
├─ 需求台账（表）            现在在哪 —— 一行一个需求，状态会被覆盖
├─ 流转记录（表）            走过的路 —— 一行一次动作，只增不改
├─ 01-需求/
│   ├─ 原始需求/             客户原话、会议记录、邮件、截图
│   ├─ PRD/                 需求规格说明书
│   ├─ 原型/                 页面流程、交互说明、设计标注
│   └─ 评审纪要/             评审结论、待确认项
├─ 02-开发/
│   ├─ 执行方案/             背景、调研、方案对比、技术设计、影响面、回滚
│   ├─ 开发计划/             任务拆分、负责人、里程碑、依赖
│   ├─ 接口文档/             路径、方法、入参出参、错误码、示例
│   └─ 数据库/               表结构变更、SQL、字段说明
├─ 03-测试/
│   ├─ 测试用例/             用例编号、关联需求ID、前置、步骤、预期
│   ├─ 测试报告/             执行统计、缺陷统计、遗留问题、结论
│   ├─ Bug清单/               编号、标题、严重级、状态、关联需求ID、修复版本
│   └─ 自动化脚本/           自动化用例代码与运行说明
├─ 04-部署/
│   ├─ 部署说明/             变更内容、影响范围、部署步骤、验证方法
│   ├─ 环境配置/             环境地址、配置项、依赖服务（**不写明文凭据**）
│   ├─ 发布记录/             版本号、发布时间、发布人、变更内容
│   └─ 回滚方案/             触发条件、回滚步骤、数据处理、责任人
├─ 05-其他/                  判不出阶段的临时归属，**不许硬塞**
└─ 00-规范/
    ├─ 研发知识库-规范总纲   给人看：放哪、叫什么、怎么流转
    └─ AI操作协议            给 AI 看：收到什么话做什么动作
```

**目录是骨架，一旦建立不允许改名、不允许挪位置。** 十年后还要能看懂。

## 三、命名规范

### 3.1 三段式

```
需求ID_文档名_v版本.扩展名
```

示例：`REQ-YF-001_PRD_v1.0.md`、`REQ-YF-001_测试报告_v1.2.xlsx`

### 3.2 需求 ID

```
REQ-<项目缩写>-<3位序号>
```

- 项目缩写：2~4 个大写字母，项目建档时定死，不再改。
- 序号：从 `001` 开始，**取需求台账当前最大值 +1**，不允许跳号、不允许复用。
- 需求 ID 由 AI 生成，不靠人记。

### 3.3 版本号

| 版本 | 含义 | 谁定 |
| --- | --- | --- |
| `v0.1` ~ `v0.9` | 草稿，随时改 | AI 自动递增 |
| `v1.0` | 第一次定稿，开发照这个做 | **定稿人拍板** |
| `v1.1` | 定稿后的小修订 | 定稿人拍板 |
| `v2.0` | 需求范围变更 | 定稿人拍板 |

**AI 不得自行升 v1.0 及以上版本。** 人没说"定稿"，就一直是 v0.x。

### 3.4 文档头四行（每篇文档开头必须有）

```markdown
> 需求 ID：REQ-YF-001
> 阶段：02-开发 / 接口文档
> 定稿人：张三
> 团队版本：v1.0
```

这四行是机器可读的锚点，也是三个月后你自己回看的索引。

## 四、两张记录表（整个体系的心脏）

### 4.1 需求台账 —— 回答"现在在哪"

| 列 | 说明 | 谁改 |
| --- | --- | --- |
| 需求ID | `REQ-YF-001`，主键 | AI 生成 |
| 需求名称 | 用人的原话提炼，不超过 20 字 | AI |
| 提出人 | 谁提的 | AI |
| 当前阶段 | 需求 / 开发 / 测试 / 部署 / 已交付 / 已归档 | AI 按流转改 |
| 定稿人 | 产品 / 开发 / 测试 / 运维 | AI 建档时填 |
| 状态 | 进行中 / 阻塞 / 已归档 | AI |

**一行一个需求。阶段一变就覆盖这一行。**

### 4.2 流转记录 —— 回答"走过的路"

| 列 | 说明 |
| --- | --- |
| 时间 | `YYYY-MM-DD HH:mm` |
| 需求ID | 关联台账主键 |
| 谁 | 发起这次动作的人 |
| 做了什么 | 一句话，动词开头 |
| 阶段变化 | `需求 → 开发`，无变化写 `-` |

**只增不改，永不覆盖。** 每次阶段推进必须写一行，且与改台账是**同一个动作**，两件一起做，不允许只改一个。

### 4.3 为什么必须是两张表

一张表存"当前状态"，一张表存"历史轨迹"。用一张表会互相打架：改了状态就丢了历史，留了历史就查不到现在。

## 五、状态机

```
需求 ──→ 开发 ──→ 测试 ──→ 部署 ──→ 已交付 ──→ 已归档
         ↑        │
         └────────┘  测试不通过，退回开发
```

**硬约束：**

- 不允许跳阶段。需求没定稿不能进开发，测试没通过不能进部署。
- 测试报告结论不通过时，**阶段不改**，并在台账状态标「阻塞」，同时指出卡在哪。
- 结项前必须逐阶段核对缺件，缺件清单给人看过之后才能转「已归档」。

## 六、AI 判定规则（规范能不能落地，全看这一节）

### 6.1 判定"这个文件放哪"—— 按顺序问三个问题

| 顺序 | 问题 | 是 → 放这里 |
| --- | --- | --- |
| 1 | 这是别人给我的原始材料吗？（客户发的、会议记录、邮件、聊天记录、截图） | `01-需求/原始需求/` |
| 2 | 这是我加工出来的吗？ | 看属于哪一步：需求设计 → `01-`，写代码/设计 → `02-`，验证 → `03-`，上线 → `04-` |
| 3 | 这是代码吗？ | **不放这里**，放代码仓库，此处只记仓库地址 + commit |

**三问都判不出来 → 放 `05-其他/`，并告知人"我暂放这里，你确认归属后我挪"。绝不硬塞进某个阶段。**

### 6.2 判定"该叫什么名"

| 情况 | 做法 |
| --- | --- |
| 已有需求 ID | 三段式命名，版本从 `v0.1` 起 |
| 还没有需求 ID | **先建档拿 ID**，再命名。不允许出现无 ID 的正式文档 |
| 人给了原文件名 | 保留原名作为「文档名」部分，不擅自改写 |
| 同名文件已存在 | 版本号 +1，**绝不覆盖** |

### 6.3 判定"该动哪张表"

| 发生了什么 | 动台账 | 动流转记录 |
| --- | --- | --- |
| 收到新需求 | 加一行 | 加一行（阶段 `- → 需求`） |
| 阶段推进 | 改「当前阶段」 | 加一行 |
| 卡住了 | 状态改「阻塞」 | 加一行，写明原因 |
| 结项归档 | 状态改「已归档」 | 加一行 |
| 日常补文档（阶段没变） | 不动 | **不动**（避免噪音） |

### 6.4 什么必须问人、什么不许编

**必须问（一次只问一个）：**

- 需求要解决什么、给谁用、现在怎么做的
- 什么算做完了（验收标准）
- 谁是定稿人
- 明确不做什么

**绝对不许编：**

- 验收标准
- 需求范围（做/不做）
- 人名、日期、版本号
- 没聊到的地方一律写「**待补充**」

> 编出来的需求比没有需求更糟——开发会照着假需求干。

### 6.5 建档要快

人说完需求，最想听到的是「**记下来了，编号 REQ-YF-007**」+ 文档链接，不是「请问目标用户是谁」。

所以顺序是：**先建档 → 再回执 → 然后边聊边补**，不要先问一堆问题。

## 七、动作 → MCP 工具映射（AI 照着调）

| 要做的动作 | 用什么 |
| --- | --- |
| 找目标集合 / 空间 | `list_collections` |
| 建阶段目录文档、子目录文档 | `create_document`（指定 `parentDocumentId` 形成嵌套） |
| 归档一篇资产 | `create_document`（`parentDocumentId` = 对应子目录文档） |
| 调整层级 | `move_document` |
| 改名 / 升版本 | `update_document` |
| 台账加行 / 改阶段 | 表格记录写入（`batch-add-records` / `batch-update-records` / `set_cell_range`） |
| 查当前状态 | 读台账表，**不要靠回忆** |
| 核对目录结构 | `list_collection_documents` 拉全树 |

**每次动手前先拉一遍目录树确认结构，不要凭记忆假设。**

## 八、七个口令（人对 AI 说的话 → AI 做的事）

| 人说的话 | AI 做什么 |
| --- | --- |
| 「这个需求……」（描述需求 / 甩来一堆材料） | 建档：取台账最大序号 +1 生成 ID → 材料存 `01-需求/原始需求/REQ-xxx_原始需求_v0.1.md` → 台账加行 → 回执 ID + 链接 + 下一个要问的问题 |
| 「** 定稿了」 | 版本升 v1.0 → 改名带版本 → 台账阶段转「开发」→ 流转记录加一行 |
| 「开发完成，在 <位置>」 | 方案/计划/接口入 `02-开发/` → 代码只记仓库地址 + commit → 台账转「测试」→ 流转记录加行 |
| 「测试通过」 | 用例/报告/Bug 入 `03-测试/` → 台账转「部署」→ 流转记录加行。**报告不通过则不改阶段，标阻塞并指出卡点** |
| 「上线了」 | 部署四件套入 `04-部署/` → 台账转「已交付」→ 流转记录加行 |
| 「结项」 | 逐阶段核对 → 列出缺件清单 → 人确认后转「已归档」 |
| 「做到哪了」 | 输出四段：当前阶段 / 已有资产 / 缺什么 / 下一步谁动 |

## 九、安全与合规（不可协商）

| 项 | 规则 |
| --- | --- |
| 明文凭据 | 环境配置、密钥、密码**一律不写进文档正文**。只写「位置」和「负责人」 |
| 敏感文件 | 含 `password` / `secret` / `token` / `.env` / 私钥特征的文件，打「敏感」标记，默认不进共享视图 |
| 凭据显示 | 会话令牌、PAT 等对外只显示前 6 位 |
| 客户数据 | 合同、客户名单等不出内网，不上公网向量库 |
| 共享粒度 | 只到项目 / 阶段 / 目录级，不做行级权限 |
| 外部共享 | 一律用带密码 + 有效期的链接，不给目录授权 |

## 十、交付给别人怎么用

这套东西**不依赖任何本地环境**，交付即用：

### 接收方三步

1. **建空间**：在协作平台建一个项目空间，按第二章建目录树（或直接复制现成空间）。
2. **导规范**：把两份文档放进 `00-规范/`。
3. **接入 AI**：让 AI 读 `00-规范/AI操作协议`，然后直接说需求即可。

### 交付清单

| 文件 | 给谁看 | 作用 |
| --- | --- | --- |
| 研发知识库-规范总纲 | 人（所有角色） | 放哪、起什么名、怎么流转、谁定稿、能不能改别人的 |
| AI操作协议 | AI | 收到什么话做什么动作、落到哪、动哪张表 |
| 需求台账 | 人 + AI | 当前所有需求的现状 |
| 流转记录 | 人 + AI | 全部历史轨迹 |

### 交接时要一并交付的

- 需求台账（当前所有需求的现状）
- 流转记录（全部历史轨迹）
- `00-规范/` 两份文档
- 空目录树骨架

**新人接收后的第一个验收标准：一小时内能从一个需求 ID 拉出它的完整链路。**

## 十一、常见问题

**Q：能不能一个空间放多个项目？**
不建议。一个空间一个项目，跨项目追溯会立刻失控。多项目请在空间之上再分一层。

**Q：文档放在这里，代码放哪？**
代码放代码仓库（GitLab）。这里只记仓库地址 + commit hash + 分支名。**不要把代码复制进知识库。**

**Q：可以改别人写的文档吗？**
不要直接改。提意见用评论；确实要改用修订模式，等定稿人审阅通过后才生效。

**Q：规范文档本身需要版本吗？**
不需要。规范直接改原文，不留版本——规范是要被所有人遵守的当前事实，不是历史记录。

**Q：AI 判错了怎么办？**
直接说「这个放错了，应该放到 XX」，AI 会 `move_document` 挪过去，并把这条判定规则补充进 `00-规范/AI操作协议`，下次不再犯。
