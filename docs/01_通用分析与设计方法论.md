## 一、方法论概述

本方法主要适用于信息系统建设、数字化、流程优化和 AI
应用项目。其他类型项目可以复用目标、证据、职责和评估思路，同时补充行业专业要求。

工作围绕四个判断展开：值得做什么、具体需要什么、如何可靠实现、最终有没有用。写文档前先确定：谁会阅读，他需要据此作出什么决定。

| 分析层次     | 思考内容                                         | 对应判断           |
|--------------|--------------------------------------------------|--------------------|
| 业务规划     | 目标、现状、原因、目标状态、能力差距、范围和分期 | 方向与投入是否合理 |
| 业务功能设计 | 场景、流程、职责、功能、规则、数据、权限和异常   | 业务能否按预期运转 |
| 实施落地     | 技术、资源、计划、测试、上线、交接和效果         | 能否交付并持续使用 |

业务架构看业务如何组织；应用架构看系统如何分工；数据架构看信息如何组织和流转；技术架构看实现与运行机制。它们是不同视角，与分析层次、文档并非一一对应。排期、预算和验收也不全属于技术架构。

**第一章先明确最终交付什么、谁使用、改善什么业务结果、本期到哪里。**
保留用户明确要求的产品、系统、智能体或能力；字典、知识库、对象模型和验证是支撑手段，不能代替最终交付。事实和约束用于检验目标，调整时说明依据。

分层允许迭代。先明确待解决问题、分析角度和预期结论，再决定是否开发页面、整理数据或调研。准备工作应消除具体未知；若已有数据和工具能回答问题，就优先复用。

## 二、核心概念

| 概念             | 一句话理解                                       |
|------------------|--------------------------------------------------|
| 业务目标         | 希望谁的什么业务结果发生变化                     |
| 问题与原因       | 问题是具体差距，原因是造成差距的机制或条件       |
| 目标业务状态     | 建成后人员、流程、信息和规则如何共同运转         |
| 业务能力         | 组织为产生业务结果必须能够做什么                 |
| 业务场景         | 谁在什么条件下，为获得什么结果处理什么事情       |
| 业务流程         | 完成结果所需的动作、决策和交接顺序               |
| 业务对象         | 表达真实业务事物或记录，具有明确含义、职责和边界 |
| 业务规则         | 行为或判断必须遵守的条件、限制与依据             |
| 功能域           | 一组功能共同承担的相对独立业务职责               |
| 功能模块         | 功能域中，为完成一项业务活动组织的一组功能       |
| 具体功能         | 系统接受什么输入、完成什么处理、形成什么输出     |
| 技术实现         | 通过什么机制满足功能与质量要求                   |
| 交付物与业务效果 | 交付物是实际提供的成果；效果是使用后产生的变化   |

“上线平台”描述交付；“减少查找与核对资料的时间”描述业务改善。“让 AI
懂研发”表达能力方向，还需要用具体场景和表现说明含义。

能力由人员、流程、规则、数据和工具共同支持，不必全部依靠新系统。功能域、模块、功能是本文约定的分析粒度，不要求固定三层，也不直接等于菜单、程序包或部署组件。

## 三、项目整体分析路径

**明确目标与本期边界 → 场景与目标流程 → 能力和知识需求 →
对象、关系与规则 → 功能设计 → 实施交付 → 业务验证与效果反馈。**

现状与证据贯穿分析。已有能力清单可以作为起点，但要通过具体场景验证和细化，不能据此直接设计知识库或对象结构。各步可反馈修正，不要求一次完成全部细节。

| 工作     | 关键提问                                                           | 最小产出                             |
|----------|--------------------------------------------------------------------|--------------------------------------|
| 需求进入 | 谁提出、谁使用、谁决策？希望改善什么，有什么期限与限制？           | 原始材料、初始目标、责任人及待澄清项 |
| 现状分析 | 当前怎么工作？问题何时发生、影响多大？原因有证据吗？               | 现状、案例、影响与待验证假设         |
| 目标状态 | 未来怎么工作？哪些流程、职责和信息需要变化？                       | 目标流程及成功表现                   |
| 能力分析 | 目标流程每一步需要什么能力、数据和知识？已有基础与真实缺口是什么？ | 能力及支撑需求清单                   |
| 路径比较 | 调整流程、培训、复用、采购或开发，哪种方式合适？                   | 选择依据和主要约束                   |
| 分期规划 | 先解决什么，依赖什么，每期能交付怎样的业务结果？                   | 阶段范围、优先级和推进条件           |

初始目标可以调整，访谈观点也需要核实。区分事实、假设、建议和决定；重要结论记录来源、适用范围、日期及确认责任人。

先用现有资料、记录和系统形成初步解释，列出证据、冲突与无法解释的情况，再针对性请专业人员确认。不要把全量材料交给业务人员，要求其代替项目组完成分析；必要的访谈、授权和专业决策仍应保留。

## 四、从业务能力到系统功能

这是本方法的核心。能力、场景和功能是多对多关系，不能从能力名称直接拆菜单，也不能将所有人工步骤原样变成按钮。

### 1. 把目标落实为本期场景

采用“谁＋触发条件＋输入＋处理任务＋输出＋验证方式”描述场景。覆盖主要正常场景、边界、异常及无法处理的情况。已有能力名称必须落到可观察的场景表现。

涉及自动生成或业务转换时，分别说明实际运行场景和历史回放等验证场景；验证场景不自动成为面向用户的产品功能。暂不覆盖的业务注明现阶段如何处理。

### 2. 推演目标业务流程

从输入到结果逐步问：谁处理、依据什么判断、输出交给谁、何时结束、异常如何返回或转交？描述未来实际使用过程，不把“调研、建字典、开发、测试”当作业务流程。

### 3. 推导能力、知识、对象和规则

沿流程逐步说明：需要理解什么业务内容，具备什么能力，依靠哪些数据与知识，已有基础和缺口是什么。先确定业务需要，再选择知识组织和技术形式。

| 分析项       | 必须解释的依据                                                               |
|--------------|------------------------------------------------------------------------------|
| 对象存在理由 | 表达什么业务事实，承担什么职责，为什么需要独立存在？                         |
| 对象边界     | 与相近对象差异是什么，哪些内容属于它，哪些不属于？                           |
| 关系与转换   | 为什么有这种关系，什么条件下如何形成输出？能否直接转换，为什么需要中间对象？ |
| 规则依据     | 来自制度、合同、业务确认还是样本推测？适用条件、反例和未知项是什么？         |
| 数据与知识   | 每一步需要什么信息，来源是否可靠，缺失或冲突时如何处理？                     |

数据库中有两张表，不足以证明两个业务对象之间的转换关系。先用代表性实例验证业务含义，再细化属性、单位、状态和映射；不为建模而增加对象，也不要求所有项目采用本体或知识图谱。

上述是分析检查角度，不是要求业务方案审批前填完全部字段和人机分工。仅将影响目标、范围或可行性的关键未知提前决策，其余在本期设计中细化。

### 4. 归纳功能域与模块

从场景步骤提取系统职责，再归纳候选功能域，最后拆模块与具体功能。已有分类可以辅助检查，不能先固定分类再强行填入功能。

| 划分标准     | 检查问题                               |
|--------------|----------------------------------------|
| 职责相对独立 | 能否用一句话说明共同承担的职责与结果？ |
| 业务边界清楚 | 负责什么、不负责什么、在哪里交接？     |
| 内部功能相关 | 是否共同支撑一类业务活动？             |
| 关联关系明确 | 与其他域交换什么信息和状态，谁负责？   |

一个流程可以跨域，共享功能需要明确维护责任。相对独立不等于没有依赖，也不代表需要独立部署。

### 5. 写清具体功能，补齐横向要求

每项功能至少说明：关联场景、触发角色、前置条件、输入、处理、输出和完成条件。再从下表检查规则是否足以支撑真实运行。

| 角度       | 必须回答的问题                                           |
|------------|----------------------------------------------------------|
| 业务规则   | 何时允许、禁止或必须执行？规则冲突由谁决定？             |
| 数据       | 含义和来源是什么，哪个记录为准，缺失或重复怎么办？       |
| 状态与版本 | 有哪些状态，谁能触发转换，是否允许撤回、重做和历史追溯？ |
| 权限       | 谁能对哪些数据执行什么操作，归属变化后怎么办？           |
| 异常与恢复 | 失败保留什么、谁接手，重试是否重复产生业务结果？         |
| 跨系统协作 | 交接如何确认，对方不可用或只完成一部分怎么办？           |
| 质量要求   | 对规模、响应时间、准确性、可用性和安全有什么要求？       |
| 人与自动化 | 哪些可自动完成，哪些必须确认，无法判断时如何转交？       |

这些要求在设计时提出，由技术方案实现。已有制度、新建议规则和技术限制应分别标明，不将技术限制静默转成业务制度。

### 6. 用案例检验设计

按“给定条件—执行动作—预期结果”推演正常、边界与异常案例。检查能否走通，责任是否有空白，结果是否可观察。原型有助于理解交互，但不能替代流程、规则和异常说明。

同时问两件事：要求是否清晰、一致且可测试；即使全部实现，是否真正支持业务目标。完整性以已定义范围为边界，不以功能数量衡量。

历史回放须避免答案泄漏：生成时不读取被验证案例的历史输出或由它提取的提示；规则归纳与独立验证分开，相关版本和近重复案例避免跨组泄漏。差异应分析为生成错误、合理变体、资料不足或历史异常，不能把历史一致率直接当作业务正确率。

### 7. 形成可交付范围

按价值、风险、依赖、工作量和验证成本确定实施安排。每项功能都须追溯到业务目标、场景或明确管理要求；管理要求注明来源和责任人。不要为了架构看起来完整而增加功能。

### 附例：服务请求处理（假设案例）

目标是减少请求遗漏；能力是接收、分派和跟踪；场景是员工提交请求并获得处理结果；流程是提交、核对、分派、处理、确认结束。

据此可归纳“请求接入与受理”等候选域，再拆出提交模块及登记、校验等功能。若约定转交需接收方确认，就要明确确认前的责任归属，并验证转交失败时责任不会丢失。

若真实原因是长期没有处理人员，仅增加登记功能无法解决问题。此例展示推导方式，不是可直接套用的功能清单。

## 五、项目文档编写方法

默认采用“业务方案 → 建设方案 →
验收记录”。实施计划放入建设方案或任务工具；复杂到需要独立管理时，再拆出实施方案。完整考虑三类方案加一类结果记录，但不以文件数量作为完整性标准。

| 文档           | 主要读者与决定                                                         | 职责与内容边界                                                                                                                         |
|----------------|------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| 业务方案       | 业务负责人、研发负责人、决策者：是否认可方向、范围和投入               | 为什么做、最终交付什么、为谁改善什么、目标场景与流程、所需能力、关键业务关系、本期范围和阶段成果；不展开字段、接口和工程任务           |
| 建设方案       | 项目与技术负责人、业务代表、研发及测试：建设哪些内容、总体路径是否可行 | 承接业务要求，统筹功能组成、关键流程规则、应用与数据关系、总体技术思路、系统集成、资源估算、建设安排、风险和验收要求；不等于纯技术方案 |
| 实施方案／计划 | 实施人员、测试、运维和项目负责人：能否按安排执行交付                   | 任务、依赖、责任、时间、环境、测试、迁移、上线、回退和交接；引用已确认设计，不重新定义业务范围                                         |
| 验收与效果记录 | 验收负责人、使用者、项目和运维负责人：交付是否合格、使用是否有效       | 实际交付版本、验证证据、遗留问题、验收结论及使用反馈；属于结果记录，不是事前方案                                                       |

详细功能设计回答系统应怎样工作，展开规则、状态、权限、输入输出和异常；详细技术设计回答怎样实现，展开接口、存储及实现机制。可作为建设方案章节、附件或已有需求设计文档，只有复杂度和协作需要时才独立成文。

| 项目情况                                           | 推荐文件安排                                             |
|----------------------------------------------------|----------------------------------------------------------|
| 小改动：单一场景、规则明确、影响有限且易回退       | 一份变更方案与验收记录，实施后补结果                     |
| 小项目：目标明确，少量功能协作                     | 建设方案＋验收记录；业务说明和实施安排合入建设方案       |
| 中等项目：多个角色、模块或系统，需要范围及资源决策 | 业务方案＋建设方案＋验收记录；实施计划作为章节或任务记录 |
| 复杂项目：跨部门、跨系统、分期或风险投入较高       | 业务方案＋建设方案＋实施方案＋验收报告；按需附详细设计   |

写任何文档前，先在工作思路中明确“文档类型、主要读者、需要作出的决定、内容边界、引用依据”。不同读者需要不同细节；同一规则只维护一个权威位置，其余引用。每章只回答一个主要问题。

独立文件是否必要，取决于是否有独立的决定、不同的读者，以及合并后是否仍容易阅读和维护。小项目可以省独立文件，不能漏掉目标范围、关键场景规则、影响对象、责任安排、验证证据和适用的恢复措施。

上述是内部项目的工作约定，不是统一行业标准。合同、采购、公司治理有明确要求时据此调整；用户当前要求优先。日常维护的四份通用资料与具体项目的交付文件数量是两回事。

总体业务方案表达目标、未来业务状态、分析结论、核心业务关系及影响决策的规则与证据。功能设计展开属性、转换条件和异常；技术方案与工作记录保存工具、SQL、源码和执行步骤。不能删掉结论依据，也不把尚未确认的推测写成既定规则。

写作时每章回答一个主要问题，每段说明它支持什么决定；合并重复观点，删除无关内容，不为凑结构增加章节。具体结构和提交前检查使用[标准方案与报告模板库](./02_标准方案与报告模板库.md)中的业务方案模板。

原始需求、评审决定、任务、测试证据保留在各自权威位置，不必复制进每份方案。测试结论、业务验收和发布批准分别明确责任人。

验收标准在功能设计时提出，实施阶段安排环境、数据、责任和证据，交付时记录结果。业务效果在真实使用后观察，不能用页面可打开或接口调用成功代替。

## 六、设计质量检查

| 检查角度         | 评审时追问                                                               |
|------------------|--------------------------------------------------------------------------|
| 目标与证据       | 最终交付、使用者、业务效果和本期边界是否清楚？是否被知识准备或建模取代？ |
| 场景与对象依据   | 输入、处理、输出是否清楚？每个对象及转换关系有存在理由和证据吗？         |
| 分析取舍         | 准备工作解决哪个未知？正文是决策所需结论，还是工具步骤与重复观点？       |
| 完整性           | 本期场景能从触发走到结束吗？边界、异常、交接和责任是否明确？             |
| 可追溯性         | 能否从功能找到业务依据，从目标找到实现及验收？变更影响能否定位？         |
| 一致性与可验证性 | 术语、规则、状态是否冲突？结果是否可观察和测试？                         |
| 实施与运维       | 依赖、资源、上线、恢复和维护是否有责任人及可执行安排？                   |
| 业务价值         | 实际使用后改善什么？会不会新增录入、复核或维护负担？                     |

效果指标说明口径、基线、目标、数据来源、观察周期和责任人，缺失时安排补测，不编造数值。记录同期人员、业务量和制度变化，避免将所有改善都归因于系统。

涉及 AI 的场景还应检查：

| 检查项   | 需要明确的边界                                         |
|----------|--------------------------------------------------------|
| 读取范围 | 允许读取哪些资料、版本，以谁的权限访问                 |
| 操作范围 | 可独立执行什么、影响哪些对象，何时停止                 |
| 专业确认 | 哪些结果由谁确认，确认前是否允许影响正式业务           |
| 不确定性 | 证据不足、来源冲突时如何说明、补充或转交               |
| 结论依据 | 如何显示来源、版本和适用条件，区分事实与推断           |
| 失败恢复 | 如何识别部分成功，避免重复执行，并重试、回退或人工接手 |
| 结果身份 | 如何区分 AI 建议、人员确认与正式结论，记录修订过程     |

将边界落实到规则和验收案例，不只是写“人工确认”或“可重试”。同时评估监督、纠正和维护成本。这份检查表不意味着要另建七个模块。

## 七、分期实施与经验复用

**区分业务能力所属阶段和自动化深度。**
已确认属于本期的能力，不能仅因工具暂不支持自动化就移出本期。人工或半自动方案须明确责任、工作量、完成标准及后续完善条件，并验证是否达到本期目标。

每期尽量交付能使用、能评价的业务过程。先做基础设施时，说明支撑的业务结果和验证方式；延期事项明确临时处理与风险。确需调整范围，应记录依据、影响和确认人。

小改动可以合为一份变更与验收记录；复杂项目可拆系统子方案，但要保留跨系统依赖和整体验收。分析深度由不确定性、错误代价和协作复杂度决定。

跨公司复用方法时，重新核实角色、术语、制度、数据归属、系统和资源条件。复用提问与判断方式，不把某公司的偏好、工具限制或内部资料当作通用规则。

每次复盘一到三个重要判断，按以下顺序记录：

**情境 → 原判断与依据 → 实际结果 → 修正认识 → 适用条件 → 方法更新。**

例如，不只写“加强沟通”，而应写清“跨部门转交曾出现无人负责，后续设计须明确接收确认前后的责任”。单个案例形成待验证经验，重复证据支持后再提炼为适用条件明确的方法。

术语积累按同义名称查重后补充；保留定义、通俗解释、使用场景、用途、示例、相近概念与来源。无法核实的标准表述标为待核实，定期修订而非只增不改。

## 九、通过 AI 协作训练分析与设计能力

本方法不仅用于指导 AI
产出文档，也用于训练本人独立思考。具体协作流程、角色模式和阶段确认点见《00｜体系使用指南与
AI 协作流程》。

### 1. 先形成自己的判断

面对重要问题，先写出自己的理解：目标是什么、已知事实有哪些、主要问题在哪里、判断依据是什么、还有什么不确定。即使答案不完整，也比直接要求
AI 给结论更有训练价值。

### 2. 让 AI 检查思路，而不是只补内容

要求 AI 检查：

- 是否把手段当成目标；
- 是否从未经核实的现象直接推断原因；
- 是否遗漏关键角色、场景、流程、规则和异常；
- 是否存在其他解释或更简单的解决路径；
- 是否把个人偏好或行业惯例误写成组织事实；
- 是否能从目标追溯到需求、设计、实施和验收。

### 3. 重要结论要求说明理由

对关键判断，至少说明：依据是什么、适用条件是什么、有什么反例、如果判断错误会有什么影响、还需要谁确认或什么证据验证。

### 4. 逐步提升独立完成比例

先由 AI 带着完成，再由本人先分析、AI 审查，最后由本人独立形成成果、AI
负责独立评审。不要把 AI 输出得快误认为个人已经掌握。

### 5. 用实际结果检验方法

项目结束后对照原目标、实际交付、测试结果和使用效果，判断哪些分析有效、哪些假设错误、哪些方法需要修订。单个案例先作为经验，经过不同项目验证后再考虑上升为通用原则。
