## ① 跟领导对方案

**1. 「假装 → 对照 → 逼近」：先用 AI 把成功的样子做出来** — [人人都是产品经理](https://www.woshipm.com/share/6440950.html)（二手，未给实证，方法可鉴）

- **做了什么**：把接需求流程改成三步——先让 AI 产出一个"看起来已经成功"的成品（哪怕是空架子原型），再拿它和真实情况对照找差距，最后一遍遍填真东西逼近。
- **打到了什么效果**：原文未给量化数据，作者自述"焦虑直接消失、不再反复改方案"。
- **用了什么方法**：核心是**先让终点可见**——你画了 A，老板想的是 B，脑子里成功的样子不同，才会反复改。
- **我能吸取什么**：方案被毙常常不是方案差，是评审会里每个人脑子里"成功的样子"不一样；把终点摆到桌上，争论就从"谁对"变成"差多少"。
- **怎么改善我的工作方式**：下次接活，先别写八章方案，让 AI 出一页"成品的样子"给领导看，让他指着说"对，我要这个"——就是让他"指认"，而不是读推导。

**2. 一页纸「目标与边界声明」+ 需求三级分级** — [和思网络·企业数字化需求定义指南](https://www.hesi.net.cn/news/hangye-zhinan/414.html)（二手，待验证）

- **做了什么**：启动前先开半天"业务目标对齐会"，产出**一页纸目标与边界声明**，由业务负责人签字、IT 不代笔；再把需求分"必须实现/可以妥协/本期不做"三级。
- **打到了什么效果**：原文未给数据。
- **用了什么方法**：三个问题逼到底——解决什么业务痛点、成功上线的可量化指标是什么、哪些流程坚决不改。
- **我能吸取什么**：需求跑偏的根因常是"由 IT 单方主导、只列功能清单、缺业务目标"。
- **怎么改善我的工作方式**：你的"跟领导对方案"缺的正是"可量化指标"和"坚决不改项"这两栏，补进你的一页决策卡。

## ② 写成 AI 能干的活（今日重点之一）

**1. GitHub spec-kit：把"二次资料"固化成人机共读的合同** — [github/spec-kit](https://github.com/github/spec-kit)（一手，150.7k star，11-19 已到 v1.4.3）

- **做了什么**：SDD（规格驱动开发）工具，把"方案定稿 → 写代码前"这段固化成派生文档链：**PRD**（为谁做/为什么/不做）→ **Spec**（可验证行为+验收场景）→ **Plan**（技术方案）→ **Tasks**（按依赖排序）→ **ADR**（单决策一页）。命令链 `specify → clarify → plan → tasks → implement → converge`。
- **打到了什么效果**：一手实测（掘金沙箱实录）——converge 在 14 个测试全过后，仍抓出一个"测试完全没覆盖"的坑：spec 要求"存档损坏给清晰提示且不被覆盖"，实际代码直接抛异常崩掉，converge 把差距追加成新任务再跑一轮。另有行业汇编口径称逻辑缺陷率约降 84%、token 约降 45%，**属厂商/行业汇总，应作区间参考非承诺**。
- **用了什么方法**：两件事最值钱——`clarify`（逼你在写码前把"所有人都以为别人会考虑"的决策摆上台面）+ `converge`（拿代码逐条对 spec/plan/tasks，只追加任务不改代码）。
- **我能吸取什么**：**spec 错了，代码会忠实地错下去**——converge 只能证明"代码符合 spec"，不能证明"spec 对"。这条永远要人来。
- **怎么改善我的工作方式**：你之前"翻译完就丢"的那份东西，正式叫法就是 Spec，是整条链里最该长期保存的资产。手上被否的方案，别急着改正文，先用 spec-kit 模板补成 Spec（重点补验收场景 + 边界情况）。

**2. SDD 不是银弹：收益只在改动 ≥3 文件时显著** — [龙虾智能体·SDD 研究](https://clawpk.net:8443/research/R-TECH-56-spec-driven-development-agent-engineering.html)（二手，引 Uvik 50 工单基准）

- **做了什么**：横评 SDD 的收益边界，引 Uvik 50 张生产 Python 工单基准。
- **打到了什么效果**：特性/数据管道工单合并率达 90%（对照 60%），但**只在改动 3+ 文件时显著**，小工单几乎无差；vibe coding 会把长期技术债反向抬高约 140%。
- **用了什么方法**：按工单规模、歧义度、受影响文件数选择性用 SDD，不是"凡事写规格"。
- **我能吸取什么**：规格的收益与改动规模强相关——小 bug 修复写完整 Spec 是浪费。
- **怎么改善我的工作方式**：B 线（存量系统小 bug）别上 SDD，直接改；只有 A 线新项目/大改动才走完整规格链。

## ③ 让 AI 写代码

**1. 字节 NL2Test：AI 生成用例 85.4% 能进 CI** — [卓码·Web 系统 AI 自动化测试](https://www.zmtests.com/skillarticle/20261023143712621)（二手，引字节实践数据）

- **做了什么**：总结"确定性测试底座 + 旁路 AI 增强层"的落地边界，引字节 NL2Test 数据。
- **打到了什么效果**：生成用例 **85.4% 能进 CI/CD**，新增用例平均约 25% 来自 Agent 生成，峰值超 50%。
- **用了什么方法**：AI 只做四类活——NL 场景转 Playwright/pytest 代码骨架、选择器失效时按可访问性快照重推理、失败后采集截图/DOM/traceback 给根因假设、从 PRD 提取功能点边界。**断言和门禁决定不交给 LLM**。
- **我能吸取什么**：AI 的真实定位是"用例转译"，不是"测试设计"——复杂业务规则正确性、模块间副作用，仍靠人。
- **怎么改善我的工作方式**：你四期要做的"用例自动化"，正确姿势是"AI 生成 + 人审断言"，不是让 AI 端到端替你测。

**2. 阿里 open-code-review：确定性管"不漏"，Agent 管"判断"** — [alibaba/open-code-review](https://github.com/alibaba/open-code-review)（一手，Apache-2.0）

- **做了什么**：把 AI 审代码拆两半——确定性工程管绝不能错的（文件选择、智能打包、规则匹配、定位/反思模块），Agent 只做动态决策（场景化提示词、工具集）。
- **打到了什么效果**：AACR-Bench（50 仓库/200 真实 PR/1505 标注）同模型下 Precision、F1 显著更高、token 约 1/9；**Recall 更低是 README 明说的有意取舍**。
- **用了什么方法**：每个相关文件打包成独立子 Agent、上下文隔离并行跑，治"覆盖不全、行号漂移、提示词一改就抖"三个硬伤。
- **我能吸取什么**：同源盲区——写代码和审代码不能用同一套逻辑，审要拆开、要有独立定位机制。
- **怎么改善我的工作方式**：测试通过后加一道**换模型独立审查**，支持 GitLab CI，可直接接进你的提交流程。

## ④ 测试和验收（今日重点）

**1. 全流程串起来的底线：确定性底座 + 旁路 AI，断言必须人管** — [卓码](https://www.zmtests.com/skillarticle/20261023143712621)（二手，数据见③-1）

- **做了什么**：给出一条可落地的全流程架构——Playwright + pytest 做确定性底座，AI 层只在语义模糊处介入。
- **打到了什么效果**：字节数据——AI 用例 85.4% 进 CI；平均自动化率约四成，用例编写和维护仍是最大短板。
- **用了什么方法**：定位**语义化优先**（getByRole/getByLabel/getByText，CSS/XPath 例外），只有语义定位失败才触发 AI 修复；AI 层必须能"无 API Key 降级"，否则一个非测试原因就能瘫痪整条链路。
- **我能吸取什么**：框架目的不是去人化，是把人从编写和修复里解放出来，集中到断言设计和风险判断。
- **怎么改善我的工作方式**：你要的"方案确定→自动生成用例→执行"最接近落地的组合就是这条；断言和门禁永远自己写，不交给 LLM。

**2. 失败诊断给根因假设，缩短排错** — [腾讯云·测试智能体体系](https://cloud.tencent.com/developer/article/2742032)（二手，引 MASTEST 论文实测）

- **做了什么**：三 Agent 协作（用例生成 / 执行自愈 / 断言报告），引 MASTEST 多智能体 REST API 测试系统。
- **打到了什么效果**：MASTEST 在 GPT-4o 和 DeepSeek V3.1 上达 94%/98% 单元测试覆盖率、100% 语法正确、bug 检出率每操作 2.13–4.50；**但系统设计保留了人工审核环节**。
- **用了什么方法**：失败后采集截图/网络日志，用 LLM 对比预期与实际，输出含根因分析和修改建议的报告。
- **我能吸取什么**：把"测试失败"从一行红字升级成可操作诊断结论，是 AI 对测试最大的价值。
- **怎么改善我的工作方式**：你现在的测试，失败后还在自己翻日志找原因；加一层"失败自动采集 + LLM 出根因假设"，先给假设再自己确认。

## ⑤ 我自己成长

**1. FDE 的能力画像是 K 型：行业洞察是主干，不是"会用 AI"** — [瞭望周刊（新华网）](https://lw.xinhuanet.com/20261123/d36fcf00029c448d945071405cd0c47a/c.html)（一手访谈）

- **做了什么**：上海交大李厚锐给 FDE 画的能力结构——一竖是行业/产线洞察（主干），下斜线是 AI 工具、数据分析、智能体搭建（技术基底），上斜线是产品迭代与机会识别（创新交付）。
- **打到了什么效果**：原文判断"行业洞察力是主干和基础，另两条互相赋能"，并强调 FDE 要在"需求不清、数据不全、条件变化"的现场判断什么问题必须突破。（转引猎聘数据：平均年薪 40.8 万、中位 36.6 万、供需比 0.28、6 月职位环比 +237.21%，未见报告原文，**待验证**）
- **用了什么方法**：把岗位与相邻角色切开——vs 售前（签约前交付方案与演示）/ vs 咨询（一次性分析建议）/ vs 外包（只对验收负责）；FDE 是采购后进场、交付跑在生产里的系统，并对业务结果负责。
- **我能吸取什么**：短板不是工具，是"安全服务这个行业的运行规律"——哪种验收材料会被甲方打回、哪条流程不能动，这类知识只能从项目里攒，学不会。
- **怎么改善我的工作方式**：每个项目结束后记一条"甲方为什么退回来"，按月归并成你自己的行业词典——本质和 ② 的 Spec 是同一件事：把口头经验变成可复用资产。

**2. 需求拆解三步法：描述复述 → 现场还原 → 重新定义** — [FDE 一线工作法](http://www.sheratonhq.com/news/191155)（二手，待验证）

- **做了什么**：把 FDE 跟客户对需求的过程拆成三步，并给出"交付物到底交付什么"的标准。
- **打到了什么效果**：原文称"超过一半的项目在第一步就埋下隐患"——双方都以为聊明白了，做出来才发现不是一回事。
- **用了什么方法**：①**描述复述**（客户说完，你用自己的话复述一遍确认）；②**现场还原**（不看 PPT 和流程图，走到实际操作的人旁边看他们怎么干活——流程图里画得干干净净的环节，实际运行中到处是人工补救）；③**重新定义**（不问"你要什么功能"，问"你希望这件事的最终结果是什么"，多数时候客户自己会发现原始需求跑偏了）。
- **我能吸取什么**：交付物不是代码，是"确定性"——你临时不在场系统也能转、业务人员会用且愿意用、出问题知道找谁。原文说能做到的项目不到一半。
- **怎么改善我的工作方式**：你出业务方案时第②步最容易省。下次去现场只看两样：一线真实在用的 Excel、以及他们手工补救的动作——那些才是规格里该写的异常分支。

## 今天最值得做的三件事

1. **把手上被否的方案，用 spec-kit 的 Spec 模板补成一份规格**（重点补验收场景 + 边界情况）——**本周做**，约 1 小时。这份 Spec 比给领导看的版本更能复用，是"翻译完就丢"问题的解药。
2. **给一页决策卡补两栏**：可量化指标 + 坚决不改项——**现在做**，10 分钟。下次跟领导对方案时用，把"不是想要的"逼成具体哪一步。
3. **在测试流程里加"换模型独立审查"**（open-code-review 支持 GitLab CI，可直接接）——**先放着**，等手头有空再评估接入成本。
